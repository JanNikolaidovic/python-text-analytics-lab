# Repo workflow

How to create a new lab, modify an existing one, and get it to students.

## Layout

```
python-text-analytics-lab/
├── solutions/labNN_<slug>/labNN.ipynb          ← MASTER. The only file you edit.
├── labs/labNN_<slug>/labNN_student.ipynb       ← GENERATED. Never edit by hand.
├── data/                                       ← course dataset (ships in the zip)
├── build_labs.py                               ← strips # @solution cells
├── new_lab.py                                  ← scaffolds a new lab
├── make_student_zip.py                         ← builds dist/python_lab.zip for the platform
├── onboarding/                                 ← video scripts + platform text for students
└── README.md                                   ← schedule
```

## How students get the labs

The GitHub repo is private. Students only ever see **`dist/python_lab.zip`**,
which you upload to the university platform. They unzip it, upload the folder
to their Google Drive, and open each lab in Colab from there (see
[onboarding/](onboarding/)). Labs that use data find the `data` folder in their
Drive with a standard cell, so the data never comes from a URL.

## The golden rule

**Edit the master under `solutions/`. Never edit anything under `labs/`.**
Files in `labs/` are regenerated by `build_labs.py`; hand edits there are
silently overwritten on the next build.

## Every session starts the same way

```bash
cd ~/repos/python-text-analytics-lab
source .venv/bin/activate        # prompt shows (.venv)
code .                           # opens VS Code (WSL Remote)
```

---

## A. Create a NEW lab

```bash
python new_lab.py 02 data_structures "Data Structures & Control Flow"
```

Creates `solutions/lab02_data_structures/lab02.ipynb` with a title skeleton
to fill in.

Then:
1. Open that master in VS Code, pick the `.venv` kernel, write the lab.
2. Mark every answer cell with `# @solution` as its **first line**.
3. If the lab uses the dataset, copy the standard Drive cell verbatim from any
   of labs 08-16 and read files through `DATA_DIR`. Run locally, it finds the
   repo's `data/` folder by itself.
4. **Run all cells top to bottom**: verify it works before publishing.
5. Build and commit:

```bash
python build_labs.py solutions/lab02_data_structures/lab02.ipynb
git add labs/ solutions/
git commit -m "Add Lab 2: data structures & control flow"
git push
```

6. Add the lab's row to `README.md`.
7. Publish to students (section D).

---

## B. MODIFY an existing lab

1. Open the **master**: `solutions/labNN_<slug>/labNN.ipynb`
2. Make the change; re-run the affected cells (or all of them).
3. Rebuild and commit:

```bash
python build_labs.py solutions/labNN_<slug>/labNN.ipynb
git add labs/ solutions/
git commit -m "Lab NN: clarify exercise 2"
git push
```

4. Publish to students (section D).

**A change is not live for students until you upload a new zip.** Editing the
master or pushing to GitHub changes nothing on their side. Students who already
copied the course folder to their Drive keep their old copy, so for a fix
mid-semester, also tell them which lab to replace.

---

## C. Rebuild everything (after a global change)

```bash
python build_labs.py solutions/*/lab*.ipynb
git add labs/ solutions/ && git commit -m "Rebuild all labs" && git push
```

---

## D. Publish to students

```bash
python make_student_zip.py        # rebuilds every student notebook, writes dist/python_lab.zip
```

Upload `dist/python_lab.zip` to the university platform. The zip contains a
student README, `labs/` and `data/`, never `solutions/` or cell outputs (the
script refuses to run if a solution cell slipped into a student notebook).
`dist/` is git-ignored.

---

## Marking answer cells

```python
# @solution
average = (r1 + r2 + r3) / 3
print("Average rating:", average)
```

The marker must be the **first non-empty line** of a code cell. Those cells are
stripped from the student build; everything else is kept.

Pattern that works well: a `# TODO` cell for students, immediately followed by
the `# @solution` cell with the answer.

---

## Before you publish: quick checklist

- [ ] Edited the master under `solutions/`, not `labs/`
- [ ] Every answer cell starts with `# @solution`
- [ ] Notebook runs top-to-bottom without unintended errors
- [ ] Ran `build_labs.py` on the master
- [ ] `git status` shows changes in **both** `solutions/` and `labs/`
- [ ] Ran `make_student_zip.py` and uploaded the new zip to the platform
- [ ] Once per semester: uploaded the zip's folder to a test Google Drive and
      opened a data lab (e.g. Lab 12) in Colab to confirm the Drive cell finds the data

---

## Notes

- **Outputs are stripped on commit** by `nbstripout`, so the repo stores only
  code and text. The zip script also clears outputs, so students always get
  clean notebooks.
- **Colab is ephemeral.** Variables and files written to `/content` vanish when
  the runtime resets; notebooks and data in the student's Drive don't.
- **Level 2 labs need installs.** Add a top cell with pinned versions, e.g.
  `!pip install -q bertopic==0.16.0`, so notebooks don't break next semester.
